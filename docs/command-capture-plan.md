# Command capture byte limits

## Objective and scope

This unit addresses H4 (bound captured command output) in
`plans/hardening-pruning-list.md`. The capture module must bound retained stdout and
stderr bytes before the command timeout.

The worker owns `src/command.ts`, its direct callers, and `tests/command_test.ts`. The
main agent owns this plan, the measurement record, documentation, verification, and the
local commit. Other backlog items remain separate.

The change does not limit workflow logs. Workflow steps continue to stream through the
runner. The change does not replace an installed binary or start another CI trigger.

## Required behavior

The capture policy declares a separate byte budget for stdout and stderr. Every current
caller must select both budgets. Timeouts and reap deadlines retain their existing values.

Output at the exact budget remains valid. If the next chunk exceeds the remaining budget,
the module rejects capture. The module must not retain the overflow chunk or allocate an
output buffer larger than the budget. The byte budgets do not claim a bound on total
process memory.

The overflow diagnostic names the command, stream, and configured byte budget. The module
must stop waiting for ordinary completion when overflow occurs. The module kills a live
direct child, closes both output pipes, and waits within the existing reap deadline.

The module must retain the overflow diagnostic if termination or pipe cleanup also fails.
If the direct child has already exited, the module closes pipes held by descendants.

Each byte budget must be a nonnegative safe integer. Invalid budgets return an error
before the module spawns a command. An empty stream remains valid with a zero budget.

Successful captures preserve status and all bytes within the budgets. Expected overflow
uses the existing `Result` type. The change adds no dependency or process framework.

## Policy and measurements

The selected policy gives ordinary helpers 1 MiB for each stream. The Swift release build
gets 16 MiB for each stream. A MiB is 1,048,576 bytes. These budgets are explicit policy
choices, not claims about measured maximum output. The user received an optional policy
question and provided no alternative before implementation.

`CommandCapturePolicy` requires `maxStdoutBytes` and `maxStderrBytes`. The four caller
modules select those values explicitly. The source monitor installer types `runChecked`
with that policy so the Swift build can select its larger budgets.

On 2026-10-04, caller measurements produced these raw byte counts on this host:

| Command category                      | Exit status | Stdout bytes | Stderr bytes |
| ------------------------------------- | ----------: | -----------: | -----------: |
| Current parent identity from `ps`     |           0 |          183 |            0 |
| Present Git configuration             |           0 |      6 or 10 |            0 |
| Absent Git configuration              |           1 |            0 |            0 |
| Git worktree root                     |           0 |           26 |            0 |
| Git active hooks path                 |           0 |           36 |            0 |
| Homebrew prefix                       |           0 |           22 |            0 |
| Homebrew service JSON                 |           0 |          582 |            0 |
| Swift version                         |           0 |           96 |           30 |
| Managed bundle owner                  |           0 |            6 |            0 |
| Managed bundle signature verification |           0 |            0 |            0 |
| Monitor process lookup                |           0 |            6 |            0 |
| Cached Swift release build            |           0 |          279 |          832 |
| Immediate warm Swift build            |           0 |          273 |          832 |

The two build measurements took 5.1 and 4.1 seconds. The builds used the existing ignored
build directory. The measurements exclude clean builds, deliberate compiler failures, and
service changes.

The main agent checked the capture pipeline with generated bytes before changing source.
The probe first produced 1,024 bytes per stream. It then changed only the block count.
Captures returned 1,048,576 and 16,777,216 bytes per stream without truncation. Those runs
took 7.01, 7.33, and 55.26 ms respectively. This probe checks byte handling and current
runtime behavior. It does not establish a safe maximum process memory usage.

The measurement record must include command category, exit status, byte counts, and limits
of the evidence. Current measurements do not establish an upper bound for future compiler
diagnostics or every repository path.

## Verification and completion

The worker adds public regression tests before changing the capture module. Tests use
small byte budgets and short native commands. The regressions must fail before the fix.

Checks cover stdout overflow, stderr overflow, exact budgets, independent budgets, zero
budgets, invalid budgets, direct child reaping, and descendant-held pipes. Existing launch
and timeout checks must retain their behavior. Each test must finish in less than one
second on this host.

The main agent reviews every changed line and runs the focused and full checks. An
independent review examines retained byte bounds, capture races, and cleanup behavior.

The local Git hook runs full verification before the unit is committed on `main`. The
repository maintainer owns pushes and selection of the next backlog item.
